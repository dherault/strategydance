# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Stack

A [Bun](https://bun.com) workspaces monorepo. Packages live under `packages/`.

- `packages/frontend` — TanStack Start in SPA mode, React 19 (with the React compiler),
  Tailwind CSS v4, built by Vite
- [oxlint](https://oxc.rs) for linting, configured in `.oxlintrc.json`
- `tsc` for typechecking; there are no TypeScript path aliases, so imports are relative
- `bunfig.toml` enforces a 7-day cooldown on installs, so a freshly published version cannot
  be installed until it has been out for a week

## Commands

| Command | What it does |
| --- | --- |
| `bun run dev` | Runs the frontend dev server on http://localhost:5173 |
| `bun run build` | Typechecks and builds the frontend |
| `bun run lint` | Runs oxlint across the repo |
| `bun run typecheck` | Runs `tsc` across the packages |

Run `bun run lint`, `bun run typecheck` and `bun run build` before every commit. The husky
pre-commit hook runs the linter, but it does not typecheck or build.

`packages/frontend/src/routeTree.gen.ts` is generated by the TanStack Router plugin on dev and
build. It is committed because `tsc` needs it, but it is never edited by hand.

## Workflow

### Granular commits

Break every unit of work into granular commits: one logical change per commit, each one
self-contained and passing lint, typecheck and build on its own. Do not bundle unrelated
changes — a dependency bump, a refactor and a feature are three commits, not one.

Write the commit subject in the imperative mood and say what the change does, not which files
it touches.

### Every unit of work happens on a branch off `dev`

`dev` is the integration branch: every pull request starts from it and goes back into it.
Never commit to `dev` or `main` directly, and never leave a branch with commits on it but no
pull request. A unit of work is finished when its pull request is merged into `dev`, not when
the code is written.

Start from an up-to-date `dev`, commit granularly, push, and open the pull request against
`dev`:

```sh
git switch dev && git pull --ff-only
git switch -c <branch>
# commit, then:
gh pr create --base dev
```

The repository's default base branch is `main`, so `--base dev` is not optional — without it
`gh pr create` targets `main`.

### Copilot review loop

Once a PR is open, drive it through review rather than handing it back unreviewed:

1. **Request a review from GitHub Copilot** with `gh pr edit <number> --add-reviewer @copilot`.
2. **Watch CI.** Wait for the checks to finish and fix anything that fails before moving on.
3. **Respond to every Copilot comment.** Each one gets a real answer: either an edit to the
   codebase that addresses it, or a reply explaining why the suggestion does not apply here.
   Never silently ignore a comment, and never resolve one without responding.
4. **Push the fixes** as their own granular commits.
5. **Re-request a review from Copilot** once the fixes are pushed.
6. **Repeat from step 2** until a review round produces no meaningful comments — pure
   nitpicks, praise, or nothing at all.

### Merge into `dev`

When a review round comes back clean — Copilot approves, or its remaining comments are pure
nitpicks or praise — and CI is green, merge the pull request into `dev` and delete the branch:

```sh
gh pr merge <number> --merge --delete-branch
```

Merge, do not squash. The granular commits are the point of the workflow, and squashing
collapses them into one.
